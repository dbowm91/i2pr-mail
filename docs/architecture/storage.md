# Storage and recovery

`i2pr-mail-store` stores metadata in SQLite and immutable raw entities as SHA-256-addressed files below the private store root. A temp file is fully written and synced before rename; the directory is synced before metadata insertion. A crash between rename and database commit can leave only an unreferenced blob. Startup removes only `*.tmp` files and never prunes committed blobs.

Schema version 4 evolves monotonically from v1: v2 adds durable outbox sender/recipient metadata and Sent entity records; v3 adds local deletion tombstones; v4 adds receive/submission state vocabulary and constraints. The base schema creates message/UIDL, draft, outbox, and raw-entity tables with a per-account unique UIDL index. A new store is created directly at the current version, while v1, v2, and v3 databases migrate in place and retain their rows.

v4 stores typed state only. The `messages.receive_state` and `outbox.state`/`outbox.stage` columns carry `CHECK` constraints generated from the domain vocabulary, so only representable state and state/progress pairs can be written at all. Migration decodes every persisted value before rebuilding those tables and aborts with an unsupported-state error when a value is unknown, rather than repairing or guessing it. The rebuild suspends foreign keys only for the copy, restores them, and verifies `pragma_foreign_key_check` afterwards. Raw message blobs are never rewritten.

The public store API takes `ReceiveState`, `SubmissionState`, and `SubmissionProgress` values rather than strings or integer stages, and `StoreError::UnknownState` is a distinct fail-closed outcome from `StoreError::InvalidStateCombination`. `scripts/check-boundaries.sh` enforces that no public store or runtime signature reintroduces an untyped state or stage parameter.

Message/raw writes commit the blob before publishing metadata. Outbox claim uses a compare-and-set update; restart maps a submission that never reached DATA to `FailedSafeToRetry` and one that may have started to `DeliveryUnknown`. Finalizing a delivery requires a submission that durably recorded `DataMayHaveStarted`, so ambiguity cannot be resolved by an automatic path. No credential input exists in the ordinary store API.

SQLite access is synchronous and one `Store` owner serializes mutable operations. Runtime must not call it from an unbounded async worker; executor integration is a runtime responsibility.
